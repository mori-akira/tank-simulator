# 0006. コードレビューはコミット前フックで強制しない

## 背景

実装セッションが自分の差分をレビューしても、同じ思い込みを二度通すだけになる。そこで、文脈を持たないサブエージェントに差分だけを見せて判定させる `/review` を用意した（[Issue #20](https://github.com/mori-akira/tank-simulator/issues/20)）。

[ADR 0005](0005-enforce-invariants-in-harness.md) は「機械的に検査できるものはハーネス側の機構で強制する」としている。この方針をそのまま当てはめると、`/review` もコミット前フックで強制すべきに見える。

## 決定

**強制しない。** `/review` はオーナーと実装セッションが必要と判断したときに実行する。

## 理由

**ADR 0005 の対象は「機械的に検査できるもの」であり、レビューはそれに当たらない。** 層の依存方向や `Math.random()` の使用は、同じ入力に対して常に同じ結果が出る。LLM の判定は出ない。合否が実行のたびに揺れるものをゲートに置くと、通らなかったときに「直すべきなのか、引き直せば通るのか」が区別できない。**揺れるゲートは、そのうち必ず迂回される。**

**通らなかったときの逃げ道が、フックには作れない。** `verify` は落ちたら直せば通る。レビューの「要対応」は、実装セッションが同意しないことがありうる。同意しない指摘を通すために、オーナーの判断を挟まずフックを黙らせる手段を用意するのなら、それは強制ではない。

**コストが毎コミットに乗る。** コミットは1つの Issue で何度も打つ。差分の大半は前回レビュー済みの続きであり、そのたびに全体を読み直させるのは釣り合わない。

## 検討した代替案

**staged diff のハッシュと合格記録を突き合わせるフック** — 記録が無ければコミットを中止する。機構としては成立し、コードを1行変えれば記録が無効になる点も正しい。採らなかったのは上記3点の理由による。特に「同意しない指摘」の扱いが、機構の側では決められない。

**CI でレビューを走らせる** — `main` 直コミット運用では検知が事後になる。ADR 0005 が CI のみを退けたのと同じ理由。加えて、揺れる判定で CI が赤くなると、CI が信用されなくなるほうの害が大きい。

## この判断を覆すとき

**「レビューを忘れた」は覆す理由になる。** ただしそのときは、揺れる判定をどう扱うか——同意しない指摘をどう通すか——を先に決めること。それを決めずにフックだけ足すと、迂回する手段が発明されて機構が形骸化する。
