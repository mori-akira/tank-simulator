# 0001. 外部ゲームエンジンを採用せず Three.js を使う

## 背景

見下ろし型の対戦車アクションを作るにあたり、Unity / Godot といった統合ゲームエンジンを使う選択肢があった。

ただし本プロジェクトはオーナーがコードを書かず、実装をすべて LLM が行う。判断軸は「作りやすさ」ではなく、**AI が自分の実装を自己検証できるか**と**検証ループが速いか**の2点になる。

## 決定

外部ゲームエンジンを採用せず、TypeScript + Three.js で構築する。

あわせて、**ゲームロジックは2D、描画のみ3D**とする。2D の `{ x, y }` から3D座標への変換は `src/render/projection.ts` だけが行う。

守るべき構造の詳細は [architecture.md](../architecture.md) を参照。

## 理由

- **AI が読み書きできる形式である。** エンジンのプロジェクトはシーングラフやアセット参照がバイナリ／独自形式のファイルに散る。テキストのソースコードだけで完結する構成なら、AI が全体を読み、差分をレビューできる
- **ヘッドレスで検証できる。** ゲームロジックが Three.js にも DOM にも依存しなければ、Node 上で数千フレームを一瞬で回せる。エンジンではエディタやランタイムの起動が必要で、検証ループが桁違いに遅い
- **ロジックを2Dに閉じることで、テストで捉えられる範囲が広がる。** 見下ろし視点では、当たり判定も弾の反射も本質的に2D問題である。3D を持ち込むのは見た目の都合にすぎない。ロジックが2Dなら、衝突や反射の正しさを数値のまま検証できる

## 検討した代替案

**Unity / Godot** — エディタ操作が前提であり、AI が単独で完結できない。オーナーが手を動かさない前提と噛み合わない。

**Phaser（2Dゲームフレームワーク）** — ロジックとフレームワークが密結合し、ゲームロジックだけを切り離してヘッドレスで回すのが難しい。自己検証の要件を満たせない。

**Three.js を使わず 2D Canvas で描画する** — 検証の観点では最も素直だが、原作の見た目を再現できない。ロジックを2Dに保ったまま描画だけ3Dにすれば、検証しやすさと見た目を両立できる。
