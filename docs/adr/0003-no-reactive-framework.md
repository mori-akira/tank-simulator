# 0003. リアクティブフレームワークを採用しない

## 背景

HUD（残弾数、勝敗表示など）の実装に React / Vue を使う選択肢があった。

## 決定

リアクティブフレームワークを採用せず、素の DOM で HUD を構築する。

## 理由

- **状態管理のモデルが二重になるのを避ける。** ゲーム状態は `WorldState` を毎フレーム破壊的に更新する形で持つ（[architecture.md](../architecture.md) 参照）。ここにリアクティブな状態管理を重ねると、「どちらが真か」が曖昧な領域が生まれる。AI が最も混乱しやすいのはこの種の二重管理であり、原因の特定に時間を取られる
- **描画タイミングを自分で握れる。** ゲームループが固定タイムステップで回る以上、HUD の更新もそのループから明示的に呼ぶのが最も素直。フレームワークの再レンダリングスケジュールが挟まると、決定論の検証範囲の外側に非同期な要素が入り込む
- **UI が小さい。** 表示するのは数個の数値とテキストだけ。宣言的 UI の恩恵が出る規模ではなく、ビルド設定と依存だけが増える

## 検討した代替案

**React** — エコシステムは最も厚いが、上記のとおり利点が出る規模ではない。仮想 DOM の差分計算と毎フレーム更新の組み合わせも噛み合わない。

**Vue** — React と同じ理由。

いずれも、HUD が「数個の数値とテキスト」を超えて複雑化した時点で再検討する余地はある。その場合はこの ADR を新しい ADR で置き換える。
